# Project Lab v1.7

Project Lab 是搭配「白板 & 心流沙盒」使用的規劃、拆解、推進、詢問、思考紀錄與經驗回用工具。

它不是另一套正式專案管理系統，也不是「把工作交給 AI」的介面。它的核心目的是讓使用者反覆練習：

> **把模糊資訊轉成可判斷、可溝通、可行動的工作，並讓過去的經驗在下一次真的派上用場。**

v1.7 把先前幾個版本的方向收斂成兩條循環：

```text
當下循環
看見資訊 → 釐清 → 拆解／判斷 → 詢問或行動 → 得到新資訊 → 修正理解

長期循環
經歷事情 → 留下思考／結果 → 沉澱案例 → 下一次找回 → 比較差異 → 修正判斷
```

因此，Project Lab **不是只有事情做完後才打開**。剛接到任務、做到一半卡住、方向怪怪的、想找人問、想確認以前是否做過，都是正常入口。

---

## 1. v1.7 這次改了什麼

v1.7 的主題是 **「經驗回用」與「任意時點進入」**。

新增：

- 主導覽新增「經驗回用」。
- 練習導航不再把使用情境暗示成線性的「規劃 → 執行 → 檢討」。
- 支援工作做到一半時重新釐清、找舊案例、比較差異。
- 案例可以是「處理中」或「已收斂」，不必等整件事完全結案。
- 快速 AI 可以協助：
  - 理解目前卡點。
  - 萃取案例搜尋意圖。
  - 從少量候選摘要中排序較相關案例。
  - 檢查「這次 vs. 過去」的類比是否合理。
  - 整理案例草稿。
- 深入討論可以選擇帶入少量舊案例摘要。
- 案例與案例回用紀錄改成獨立 Firestore documents，不塞進 Project Lab 主 document。
- 原「檢討與決策」改成「思考與決策」，避免誤以為只有事後才能留下紀錄。

沒有做：

- 全量歷史自動送給 AI。
- Embedding / Vector Search / RAG Server。
- 自動套用舊案例答案。
- AI 自動改正式白板。
- 案例管理 Dashboard。

這些不是做不到，而是目前會讓系統複雜度長得比能力快。這種事情軟體界很擅長，不必跟著學。

## 3. 兩個工具的責任要分開

### 正式白板

代表「目前正式採用的工作方式」與「已發生事實」。

白板負責：

- 排程卡／自由卡。
- 日期與預估工時。
- 實際工時與工作紀錄。
- 下一步／下一判斷點。
- 預期產出／驗收。
- 正式進度與狀態。
- 發想節點。

### Project Lab

代表「思考中的理解、練習、候選方案與經驗」。

Project Lab 負責：

- 目的／目標／目前做法。
- 已確認依據 vs. 我的理解。
- 拆解練習。
- 管理事項。
- 詢問整理。
- 快速分析。
- 思考／檢討紀錄。
- 重要發現。
- 決策紀錄。
- 歷史狀態。
- 修改建議。
- 重新規劃方案。
- 經驗案例與經驗回用。

Project Lab **不直接改白板**。真正採用之後，仍由使用者回白板調整正式資料。

## 4. Project Lab 不是「檢討工具」，而是工作中的思考入口

你可以在下列任一時點進入：

### 剛接到事情

可能需要：

- 釐清真正目的。
- 分辨需求方已確認內容與自己的推定。
- 查以前有沒有類似案例。

### 開始規劃

可能需要：

- 目的／目標／目前做法分開。
- 拆解工作。
- 估計依賴與驗收。

### 做到一半卡住

可能需要：

- 判斷是缺資訊、缺決策、缺人、還是工作拆錯。
- 找人問。
- 查舊案例。
- 回頭檢查原本前提。

### 有新資訊

可能需要：

- 修正管理事項。
- 留下重要發現。
- 更新判斷。
- 看是否需要重新規劃。

### 做完一段或結束

可能需要：

- 結果回顧。
- 決策紀錄。
- 沉澱成可回用案例。

## 5. 七個主分頁

### 5.1 練習導航

當你連「現在到底卡在哪」都不清楚時使用。

目前入口：

1. 釐清專案。
2. 拆解工作。
3. 推進與詢問。
4. 判斷與選擇。
5. 經驗回用。
6. 回頭釐清／檢討。
7. 重新規劃。

也可以使用「幫我判斷現在聚焦哪裡」，讓快速 AI 只做**情境路由**，不直接把整個專案重新分析一遍。

### 5.2 釐清專案

核心三欄：

- **目的**：真正想解決什麼問題／改變什麼狀態？
- **目標**：目前期限內要達到什麼可判斷的狀態？
- **目前做法**：現在暫時準備怎麼做？

再額外區分：

- 目前確認程度。
- 已確認的依據。
- 我的理解／推定。

這是 v1.6.4 起的重要防偏移機制。

### 5.3 拆解工作

包含：

- 工作總覽。
- 拆解練習。

拆解練習順序：

1. 為什麼需要拆？
2. 我自己先怎麼拆？
3. 哪些是獨立成果、哪些只是步驟、哪些仍需探索？
4. 拆完後最先推進哪一塊？
5. 再讓快速 AI 檢查粒度與邊界。

不是「AI 幫我代拆」。

### 5.4 推進與詢問

處理不是單純執行工作、而是需要管理的事項。

思考狀態：

```text
抓住 → 釐清 → 判斷 → 推進 → 收斂
```

典型問題：

- 我缺什麼資訊？
- 誰可能知道？
- 誰有權決定？
- 誰執行？
- 現在球在誰手上？
- 何時再追？

### 5.5 經驗回用

v1.7 新增。

用途不是「查以前答案」，而是：

> **以前有沒有碰過？當時誰處理？怎麼處理？這次相似到什麼程度？**

詳細流程見第 9 節。

### 5.6 思考與決策

這裡不是只有事後檢討。

可以在工作進行中保存：

- 一次有價值的快速分析。
- 一次重新釐清後形成的理解。
- 一個重要發現。
- 一個真正形成的決策。

也可以在事情完成後做結果回顧。

子區：

- 思考／檢討紀錄。
- 重要發現。
- 決策紀錄。

### 5.7 版本與方案

只有規劃變動較大時才進來。

包含：

- 歷史狀態。
- 修改建議。
- 重新規劃方案。

重新規劃前先判斷：

- 只是手段要改？
- 目標可能要重新確認？
- 對問題／目的的理解可能改變？

後兩種情況先重新定錨，不直接拿舊前提重排卡片。

## 6. AI 分工：三種用途，不是三個人格

### 6.1 快速 AI：短迴圈

Project Lab 直接呼叫使用者貼入的 Gemini API Key。

適合：

- 解讀目前介面／情境。
- 判斷目前最適合去哪個練習區。
- 規劃基礎檢查。
- 拆解回饋。
- 找資訊缺口。
- 整理詢問。
- 找相似案例。
- 比較少量舊案例與現在情境。
- 整理案例草稿。

快速 AI 的主要目標：

> **找出下一個值得處理的問題、證據或小動作。**

不是替使用者完成整套規劃。

### 6.2 深入討論：長迴圈

Project Lab **不直接串付費聊天 API**。

它會整理一份 Context，讓使用者複製到平常使用的 ChatGPT、Gemini 或其他完整對話環境。

適合：

- 問題本身可能定義錯。
- 目的／目標存在歧義。
- 多方立場需要折衷。
- 多個方案都有真正取捨。
- 要跨很多案例觀察自己的長期思考模式。
- 需要多輪推敲，而不是一輪 1～3 點回饋。

v1.7 可以在「經驗回用」勾選少量案例，帶入深入討論。

### 6.3 結構化匯入：把已形成共識整理回工具

修改建議 JSON、重新規劃 JSON 屬於結構化用途。

它的正確順序是：

```text
先思考／討論 → 形成方向 → 再結構化 → 匯回 Project Lab
```

不是：

```text
叫 AI 直接生一套完整方案 → 因為 JSON 很完整所以假裝它很合理
```

## 7. 快速 AI 如何避免被使用者主觀一路帶偏

快速 AI 內建的基本規則：

1. 分開已知事實、使用者推論、未知。
2. 先檢查「我目前怎麼看」的依據，不直接覆蓋成 AI 自己的答案。
3. 不因為使用者提出某個手法，就把那個手法當成目標。
4. 每輪最多先處理 1～3 個真正重要的點。
5. 新增分析分支前，先問它是否會改變目的、決策或下一步。
6. 若資訊已足夠，明確指出可以先行動。
7. 若方案越談越複雜，重新回到已確認目的／目標／限制。
8. 舊案例只能作為參考，不能因為「以前這樣做」就直接推出「這次也該這樣做」。

## 8. 整理詢問：把問題縮到別人容易回答

「整理詢問」不是替你寫一封完整專案 briefing。

它會問：

- 我想問誰？
- 希望這次對話怎麼進行？
- 我最希望得到什麼？

對話方式：

- 回答一個具體問題。
- 分享你的經驗。
- 幫我檢查目前想法。
- 跟我一起把問題想清楚。

尤其對不是專案負責人的同事／朋友，原則是：

> **只提供他回答這一題需要知道的最少背景。**

## 9. 經驗回用：v1.7 的核心新增流程

### 9.1 找相似經驗

輸入：

> 我現在遇到什麼？

例如：

```text
需求還沒完全確認，但已經開始談技術方案。
我想知道以前是否也發生過「手段比目的先被定案」的情況。
```

搜尋流程：

```text
目前情境
  ↓
快速 AI 萃取問題類型與 3～6 個搜尋概念
  ↓
Firestore 只查少量候選案例摘要
  ↓
快速 AI 對最多 8 筆候選摘要做相關性排序
  ↓
顯示最多 5 筆
```

一次「找相似經驗」最多使用兩次快速 AI 呼叫。

### 9.2 搜尋結果會顯示什麼

- 案例標題。
- 處理中／已收斂。
- 問題類型。
- 標籤。
- 摘要。
- 為什麼可能相關。
- 最值得先注意的差異。
- 處理者／可詢問的人。
- 處理時間。
- 已回用次數。

### 9.3 拿一筆案例來對照

使用者先填：

- 我覺得相似的地方。
- 這次不同的條件。
- 我目前覺得可以沿用的部分。
- 不能直接套用／需要再確認的地方。

然後才按：

> 快速 AI：檢查我的比較

AI 的任務是檢查類比，不是替你複製上次答案。

### 9.4 紀錄這次回用

最後可以標記：

- 仍適用。
- 部分適用。
- 不適用。

按「紀錄這次回用」後：

- 產生一筆 `experienceUses` document。
- 原案例的 `reuseCount` +1。
- 更新 `lastUsedAt`。
- 保存這次「哪裡像／哪裡不同／哪些可以用」。

這讓未來不只知道「案例存在」，還可以逐漸看到「這個經驗後來被怎麼修正」。

### 9.5 案例可以是處理中

不是只有完美結案才能留下。

例如：

```text
問題：某類公文以前是否處理過？
處理者：前任承辦 A
目前已知：去年有前案、當時先問法務
狀態：處理中
```

光這些資訊，下次再遇到就已經有價值。

處理中的案例要明確標示，不把暫時處理方式當成成熟原則。

## 10. 如何沉澱一筆案例

「經驗回用」頁底部有「沉澱目前經驗成案例」。

最小值得留下的資訊：

- 案例標題。
- 問題類型。
- 狀態：處理中／已收斂。
- 摘要。
- 處理者／可詢問的人。
- 處理時間。
- 目前／最後怎麼處理。
- 結果。

進階但很有價值：

- 一句話經驗。
- 主要取捨。
- 適用條件。
- 不能直接套用的條件。

可以：

- 手動填。
- 從目前情境預填。
- 用快速 AI 整理草稿，再由使用者檢查後保存。

AI 不會自動保存案例。

## 11. 案例庫資料結構與效能設計

### 11.1 Project Lab 主狀態

主狀態仍使用：

```text
ProjectLab_Data/{uid}
```

包含：

- projects
- managementItems
- breakdownPractices
- reviews
- findings
- decisions
- snapshots
- patches
- scenarios
- analysisByProject
- recentProjectIds

### 11.2 案例庫

v1.7 新增：

```text
ProjectLab_Data/{uid}/experiences/{experienceId}
```

每一筆案例獨立成 document。

原因：

- 不讓主 Project Lab document 無限變大。
- 搜尋時只取需要的案例。
- 案例可以跨專案。
- 案例數量增加時仍能維持合理讀取量。

### 11.3 回用紀錄

```text
ProjectLab_Data/{uid}/experienceUses/{useId}
```

只在使用者主動按「紀錄這次回用」時建立。

### 11.4 案例不複製完整原始資料

案例只保存：

- 標題。
- 摘要。
- 類型與標籤。
- 處理者／日期。
- 處理方式／結果／經驗／取捨。
- 適用條件。
- 原始來源的 Project / Entity ID。

不複製：

- 整個 Snapshot。
- 全部 workLogs。
- 全部 entries。
- 完整 AI 對話。
- 所有專案卡片。

原始資料繼續留在原工具。

## 12. 為什麼 v1.7 還不做 Vector Search

Firestore 與其他後端都可以再往 embeddings／向量搜尋發展，但 v1.7 刻意不做。

目前流程：

1. 快速 AI 把自然語言轉成固定問題類型與關鍵概念。
2. Firestore 用問題類型／`searchTerms` 找候選。
3. 候選不足時才取少量最近案例補足。
4. 最多 8 筆摘要交給快速 AI 排序。

先觀察：

- 案例數量真的成長到多少？
- 關鍵字／類型是否開始常常找不到已知案例？
- Firestore reads 是否真的成為問題？

真的需要時再升級語意搜尋。

## 13. 資料保存規則

### 自動保存在本機

- 專案目的／目標／做法。
- 已確認依據／我的理解。
- 目前問題／補充情境／目前看法。
- 管理事項。
- 拆解練習。
- 案例草稿。
- 思考／檢討紀錄。
- 重要發現。
- 決策。
- Snapshot / Patch / Scenario。

localStorage key：

```text
project_lab_state_<Firebase UID>
```

### 按「備份練習資料」才備份主 Project Lab 狀態

```text
ProjectLab_Data/{uid}
```

### 案例是另外一條保存路徑

按「保存案例」後立即寫入：

```text
ProjectLab_Data/{uid}/experiences/{experienceId}
```

按「紀錄這次回用」後立即寫入：

```text
ProjectLab_Data/{uid}/experienceUses/{useId}
```

因此案例不受「備份練習資料」按鈕控制。

### 不保存

- Gemini API Key。
- 尚未採用的快速 AI 回覆。
- 暫時 Prompt。
- 整理詢問輸出。
- 深入討論輸出。
- 案例搜尋結果本身。

### 只有主動保存才進歷史

快速 AI 結果按「保存這次分析」後，才進思考／檢討紀錄。

## 15. Firestore Rules：v1.7 必須更新

v1.6.4 只有：

```text
ProjectLab_Data/{uid}
```

v1.7 新增子集合，因此必須發布 ZIP 內新的 `firestore.rules.txt`，或至少加入：

```text
match /ProjectLab_Data/{userId} {
  allow read, write: if request.auth != null && userId == request.auth.uid;

  match /experiences/{experienceId} {
    allow read, write: if request.auth != null && userId == request.auth.uid;
  }

  match /experienceUses/{useId} {
    allow read, write: if request.auth != null && userId == request.auth.uid;
  }
}
```

Firestore Rules 的 parent match 不會自動讓 subcollection 繼承相同權限，所以這一步不能省。

若忘記更新，Project Lab 主資料仍可能正常，但「案例庫」會出現 `permission-denied`。

## 18. 第一次使用 v1.7 建議順序

不要一次把所有功能都摸一遍。

### 先做這四件事

1. 發布新版 Firestore Rules。
2. 覆蓋 GitHub Pages 的六個檔案。
3. 打開 Project Lab，確認舊資料仍存在。
4. 用一個真實、正在發生的問題測一次「經驗回用」。

### 第一個案例可以很簡單

例如：

```text
標題：月報不能最後一天才開始整理
類型：排程／工時
狀態：已收斂
處理者：前輩分享
摘要：月報亮點與問題若只在月底整理，容易找不到脈絡，應在週期中累積。
一句話經驗：週期性報告的素材要在過程中累積，不是月底才回憶。
```

有 3～5 筆真案例之後，再評估搜尋效果，會比先設計一整套分類法可靠得多。

## 20. 常見誤用

### 誤用 1：AI 一開始就替我規劃完整

應改成：

> 先問現在最值得確認哪 1～3 件事。

### 誤用 2：找到舊案例就直接照抄

應改成：

> 先比較相似條件與不同條件。

### 誤用 3：所有工作都沉澱成案例

案例至少要有一個理由：

- 下次可能再遇到。
- 知道誰處理過很有價值。
- 有一個值得重用／避免的判斷。
- 有重要取捨或條件。

「今天把檔案上傳成功」通常不需要寫成組織智慧。地球可以承受少一筆。

### 誤用 4：案例一定要結案才能寫

不需要。

處理中案例只要清楚標示「處理中」，也可以保存已知脈絡與處理者。

### 誤用 5：把 Project Lab 當正式資料來源

正式執行事實仍以白板為主。

## 21. 故障排除

### 找不到正式白板資料

確認：

- 白板與 Project Lab 在同一 GitHub Pages origin。
- 使用同一登入帳號。
- 白板已經有 localStorage 資料。

### 案例庫顯示 permission-denied

優先檢查：

- Firestore Rules 是否已發布 v1.7 子集合規則。
- 目前 Firebase Auth 是否登入。

### Gemini 顯示 API Key / quota 錯誤

- Key 不會保存，重新整理後需要重新貼。
- 三組 Key 依序輪換。
- 如果是模型名稱錯誤，不應靠換 Key 解決。
- 可以按「檢查模型／連線」。

### 找相似經驗完全搜不到

先確認：

- 已經真的保存過案例。
- 案例問題類型／標籤是否有基本資訊。
- 目前描述是否太像專案專有名詞，沒有說明真正卡點。

若案例累積很多後仍反覆搜不到已知案例，才是考慮向量搜尋的訊號。

## 23. v1.7 的北極星

這套工具長期是否有價值，不看它有多少功能，而看兩件事：

1. **遇到混亂資訊時，使用者是否越來越能自己辨識下一個值得處理的問題。**
2. **下一次碰到類似情況時，是否不用再從零開始，而且仍能判斷舊經驗這次是否成立。**

最終希望是：

> 就算哪一天拿掉 Project Lab，使用者仍然比以前更會釐清目的、拆解問題、詢問、判斷、推進與回用經驗。

如果反而變成「沒有這個工具就不知道怎麼想」，那工具雖然功能很多，目的卻失敗了。
